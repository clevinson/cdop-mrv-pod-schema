# CDOP MRV pod schemas

A small LinkML proof of concept translated from `MRV August 11.xlsx` for discussion
with the CDOP MRV pod. All definitions live in [schema/mrv-pod.yaml](schema/mrv-pod.yaml),
with comments separating the entities and picklists. Edit that file going forward;
the corrected workbook is a one-time snapshot to share with the group.

Generated documentation uses **Field/Fields** to match the workbook. The docs build
updates labels and prose while retaining LinkML terminology in source snippets and URIs.
The published site opens directly on the schema reference, with its introduction
drawn from the schema's `description`. This README stays in the repository for
contributors and is not published as a documentation page.

## Local commands

Install [uv](https://docs.astral.sh/uv/getting-started/installation/) and Make.
Make is available with macOS developer tools and on the GitHub Ubuntu runner.
Run these commands from the repository root:

```sh
uv sync --locked
make schema      # build/mrv-pod.schema.json
make validate    # schema + both example Project records
make docs        # build/site/index.html
make serve       # http://127.0.0.1:8000
```

`uv.lock` pins the dependencies. There is no Python package to install or publish.
`build/` and `.venv/` are ignored by git. Rerun `make docs` after schema edits;
`make serve` builds once before starting the preview server.

`build.py` holds the small documentation customizations and LinkML compatibility
helpers used by Make. Run `uv run --locked python build.py --help` to see its
commands, or `uv run --locked python build.py customize-docs` to reapply the
customizations to generated Markdown.

The examples are fictional and contain only required fields for the objects shown:

- [Minimal project](examples/Project-minimal.yaml).
- [Project with monitoring and attestation](examples/Project-with-monitoring.yaml).

Validate your own YAML or JSON Project record with:

```sh
make validate EXAMPLES=path/to/project.json
```

Validation uses LinkML's CLI and its built-in JSON Schema plugin. Each
`make validate` run generates configuration for the selected files and calls
`linkml validate --config build/validation.yaml` with those filenames. Filenames
must also be passed on the command line: LinkML 1.11.1 otherwise consumes its
configuration-only input iterator before validation begins.

The configuration selects LinkML's built-in `YamlLoader` for both YAML and JSON.
This preserves nulls and empty values; LinkML 1.11.1's default JSON loader removes
some of those values before validation and can crash on null array entries.

LinkML 1.11.1 does not yet emit the `extra_slots` setting for open objects. The
build helper copies that setting from the schema into the generated `JsonObject`
definition's `additionalProperties`. Everything else is generated by LinkML.
The CLI validates against this exact artifact, so arbitrary JSON keys are allowed
inside the four input/output arrays while unknown fields elsewhere are rejected.
Array items must be objects; scalars, null items and empty required arrays fail.
External JSON Schema consumers should enable format checking for dates and URIs.

## Workbook translation

The schema retains descriptions, picklists, field IDs, spreadsheet cell references,
and the source/visibility/mutability/pre-issuance columns as annotations. Blank
metadata stays unspecified. Cell comments in the workbook explain changes and
retain original values.

- Consolidated duplicate `Project.reporting` rows into one Public / Private,
  Mutable field, retaining both descriptions. Reused the duplicate row for the
  optional `Project.attestation` connection.
- Made `source_of_data`, `qa_qc_procedures`, and `purpose_of_data` cardinalities
  agree with their Required labels: `1..*`, `1..1`, and `1..*`.
- Made `monitoring_parameter` one picklist value per plan or result.
- Represented input/output data and variables as required, nonempty arrays of
  `JsonObject`; normalized their four field names to lowercase snake_case.
- Filled the missing `MonitoringPlan`/`MonitoringResult` relationship types.
- Represented file uploads as URI references and date ranges as `DateRange`
  objects with required `start_date` and `end_date`. Quote dates in YAML.
- Normalized cardinality whitespace and Required/Yes capitalization.

Visibility, mutability and pre-issuance annotations are descriptive, not access
controls or workflow rules. Conditional worksheet/evidence requirements remain
documented rather than enforced. `hwp_worksheet` retains the original ambiguous
requirement text and follows its `0..1` cardinality. Date ordering, indicator
cross-references, alignment of parallel indicator lists, and automatic unit-symbol
derivation are not validated. `unit_type` includes Date, but the workbook supplies
no corresponding unit symbol; the original picklists are preserved.

The `https://example.org/cdop/mrv-pod` schema identifier is a placeholder, not a
published vocabulary. Replace it and the `mrv` prefix when the pod chooses a
permanent namespace.

## GitHub Pages

The workflow validates examples and builds documentation on pull requests. Pushes
to `main` also deploy the built site through GitHub Pages. It can be run manually
on `main` from the Actions tab.

1. Push this repository to GitHub when you are ready.
2. In **Settings → Pages → Build and deployment**, choose **GitHub Actions**.
3. Push to `main` or run **Validate and publish docs** from the Actions tab.

The deployment job reports the site URL. No `gh-pages` branch or personal token is
needed. Generated docs include downloadable LinkML and JSON Schema files; the
workbook stays in the repository. To change the publish branch, update both the
trigger and the deployment conditions in `.github/workflows/pages.yml`.

This takes its uv, LinkML documentation generator and MkDocs approach from
[linkml-project-copier](https://github.com/linkml/linkml-project-copier), with a small
Makefile because these tasks do not need an additional task-runner installation.
Deployment follows [GitHub's Pages artifact workflow](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).
